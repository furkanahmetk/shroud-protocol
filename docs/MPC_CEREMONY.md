# Shroud — MPC Trusted Setup Ceremony

**Status:** Planning draft
**Roadmap task:** #14 (P3)
**Target completion:** Before mainnet launch, runs in parallel with the audit (#12).

The current `withdraw_final.zkey` was generated by a single contributor.
For mainnet, the proving key must come from a multi-party computation (MPC)
ceremony so that **as long as a single contributor is honest**, no party
can forge proofs.

This doc is a plan, not a guide for an existing ceremony.

---

## 1. Background — what we have today

- **Circuit:** `circuits/withdraw.circom` (depth-20 Merkle tree, 5 public
  inputs, MultiMiMC7 hash).
- **Powers of Tau:** Phase 1 of Groth16 trusted setup. We reuse a public
  Powers of Tau ceremony (e.g. the Hermez or perpetual-powers-of-tau
  transcript). **Do not re-do Phase 1** — there is no need and it would be
  insecure unless run with thousands of contributors.
- **Phase 2 (current):** single contributor, sufficient for testnet only.
- **Phase 2 (mainnet target):** ≥ 5 contributors, diverse hardware, public
  attestations.

---

## 2. Goals

1. Each contributor's randomness genuinely cannot be reconstructed by the
   others.
2. The full transcript is publicly verifiable end-to-end.
3. The final zkey hash matches the on-chain `vk.rs` modulo the standard
   Powers-of-Tau-to-circuit transform.
4. The ceremony is performed against the **exact circuit committed at the
   audit-sealed SHA** — no last-minute circuit changes.

---

## 3. Contributor recruitment

Target ≥ 5 contributors. Prefer at least one from each of these buckets:

| Bucket | Why |
|---|---|
| Casper Network core / validator | Domain credibility |
| ZK researcher (academia or established lab) | Cryptographic rigor |
| Other privacy-preserving project (Aztec, Penumbra, Tornado fork) | Cross-ecosystem trust |
| Independent security researcher with public reputation | Adversarial mindset |
| Project team member | Coordination, last fallback |

**Diversity guarantees** the MPC bound is meaningful:
- Different physical locations
- Different operating systems / hardware
- Different randomness sources (HRNG, mouse jitter, ambient noise)
- No two contributors known to share an infrastructure provider

---

## 4. Ceremony tooling

| Tool | Use | Notes |
|---|---|---|
| **snarkjs** (`zkey contribute`) | Reference implementation | Simplest; widely used. We're already on snarkjs. |
| **Polygon Hermez `phase2-bn254`** | Battle-tested alternative | Slightly more involved tooling. |
| **trusted-setup-mpc orchestrator scripts** | Sequence + transcript verification | We'll write a tiny wrapper that calls snarkjs and pins the contributor order. |

**Choice:** snarkjs CLI + a thin orchestrator that:
- Records each contributor's commit (hash of the new zkey)
- Publishes each intermediate zkey + the contributor's beacon hash + a
  GPG-signed attestation
- Runs `snarkjs zkey verify` between each contribution against the previous
  one

---

## 5. Sequence

```
[T-2 weeks]  Lock circuit at audit-sealed SHA, publish r1cs hash
[T-1 week]   Recruit contributors, publish public schedule + verification script
[T0]         Ceremony coordinator publishes `withdraw_0000.zkey` (Phase-1 PoT → circuit-specific)
[T0 + Nd]    Contributor 1 runs snarkjs zkey contribute,
             commits `withdraw_0001.zkey` + signed attestation
... repeats for all contributors ...
[T+N+1d]     Final beacon: a public, unpredictable value (e.g. recent
             Bitcoin block hash, or NIST randomness beacon) applied via
             `snarkjs zkey beacon` to bind the ceremony's end
[T+N+2d]     `withdraw_final.zkey` published; `snarkjs zkey export verificationkey`
             produces JSON; we re-run our `vk.rs` generator and diff
[T+N+3d]     Open verification window — anyone can re-run the transcript
             check and publish disagreements
```

Calendar budget: ~3 weeks for 5 contributors, including diff-resolution time.

---

## 6. Verification artefacts

For the ceremony to be auditable, publish:

- `transcripts/withdraw_phase2/`
  - `pot_link.txt` — link + sha256 of the Powers of Tau file used
  - `circuit_r1cs.sha256` — circuit fingerprint at start
  - `00_initial.zkey` … `0N_final.zkey` — all intermediate zkeys
  - `attestations/0N.signed.txt` — each contributor's GPG-signed
    description of their setup, randomness source, software version
  - `beacon.txt` — the public beacon value + source
  - `verify.sh` — script to walk the chain end-to-end
- Pinned IPFS / Arweave mirror in case the GitHub repo moves

The audit firm (#12) should also review these artefacts, not just the
contract code.

---

## 7. Update path

Once the ceremony completes:

1. Replace `circuits/withdraw_final.zkey` with the ceremony output.
2. Re-export the verification key as JSON.
3. Regenerate `contracts/src/vk.rs` from the JSON (commit hashes diff = audit
   review item).
4. Rebuild + redeploy the contract — this is a NEW contract package on
   mainnet, NOT an upgrade to the testnet contract.
5. Frontend / CLI configs point at the new contract package hash.
